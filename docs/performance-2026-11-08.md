# ผลปรับประสิทธิภาพ Khao Piek POS — 8 พฤศจิกายน 2026

ปรับโค้ดและสร้างไฟล์เว็บเรียบร้อย โดยวัดก่อน–หลังและตรวจขั้นตอนใช้งานทั้งลูกค้าและหลังบ้าน ผลนี้เป็นเวอร์ชันในเครื่อง ยังไม่ได้เผยแพร่แทนเว็บออนไลน์

## ผลวัดก่อน–หลัง

จำลองมือถือ 390 × 844, CPU ช้าลง 4 เท่า, เน็ตดาวน์โหลด 1.6 Mbps และ latency 150 ms เปิดใหม่แบบไม่มีแคช 3 รอบ ใช้เมนูจำลอง 24 รายการ โต๊ะ 12 โต๊ะ และรูปชุดเดิมทุกไบต์ทั้งสองเวอร์ชัน API ใช้ข้อมูลทดสอบ จึงไม่ใช่ผลวัดความเร็วอินเทอร์เน็ตหรือ Supabase จริง

| หน้าลูกค้า | ก่อน | หลัง | ลดลง |
|---|---:|---:|---:|
| JavaScript ที่โหลดเริ่มต้น (gzip) | 172,644 B | 103,862 B | 39.8% |
| CSS (gzip) | 26,975 B | 8,388 B | 68.9% |
| ฟอนต์ที่ดาวน์โหลด | 153,380 B | 67,640 B | 55.9% |
| เวลาเมนูพร้อมแสดง ค่ากลาง | 1,831 ms | 1,442 ms | 21.3% |
| เริ่มเห็นเนื้อหา FCP ค่ากลาง | 1,504 ms | 788 ms | 47.6% |
| เนื้อหาหลักแสดงครบ LCP ค่ากลาง | 5,836 ms | 5,072 ms | 13.1% |

หน้าหลังบ้านโหลด JavaScript เริ่มต้นลดลง 20.0%, CSS ลดลง 27.4% และปริมาณทรัพยากรรวมลดลง 31.3% การแบ่งไฟล์ทำให้จำนวนคำขอเริ่มต้นของหน้าลูกค้าเพิ่มจาก 13 เป็น 21 แต่ส่งข้อมูลน้อยลงและผลเวลาเปิดเมนูดีขึ้นในการทดสอบนี้

รูป JPEG ในโฟลเดอร์ public/images มีการปรับขนาดจากงานที่ทำควบคู่กัน จึงให้การวัดรอบสุดท้ายใช้รูปเดิมจาก baseline เพื่อแยกผลของโค้ดและฟอนต์ออกมา ตัวเลขนี้ไม่ได้นับการบีบอัดรูปนั้นเป็นผลประหยัดเพิ่มเติม และไม่ใช่การวัดรูปเมนูจริงทั้งหมดบน Supabase Storage

## สิ่งที่ปรับ

- แยกทางเข้าหน้าลูกค้ากับหลังบ้าน และแยก CSS ส่วนกลางออก หน้าลูกค้าไม่โหลดหน้าต่างรับเงิน รายงาน หรือรูปแบบหลังบ้าน
- โหลดหน้าเพิ่มเมนู รับออเดอร์พนักงาน และหน้าจัดการต่าง ๆ เมื่อเปิดใช้งาน ลดงานเริ่มต้นของหน้าโต๊ะ
- ให้ลูกค้าใช้การเรียก RPC แบบ anonymous ขนาดเล็ก แทนการดาวน์โหลด SDK ที่รวม Auth, Storage และ Realtime ของพนักงาน โดยคงการตรวจข้อมูลและคำสั่งซื้อเดิม
- ตรวจความพร้อมฐานข้อมูลกับโหลดเมนูครั้งแรกพร้อมกัน และรอให้ตรวจผ่านก่อนแสดงเมนู การรีเฟรชเมนูครั้งถัดไปเรียกเมนูเพียงรอบเดียว
- หยุดดึงประวัติออเดอร์เมื่อซ่อนแท็บ และตรวจทันทีเมื่อกลับมาเปิดหรือออนไลน์อีกครั้ง คำขอประวัติไม่ซ้อนกัน แม้สถานะการส่งออเดอร์เปลี่ยนระหว่างรอคำตอบ
- เก็บ reference ของข้อมูลที่ไม่เปลี่ยน ลดการวาดหลังบ้านซ้ำจากการตรวจออเดอร์เดิม พร้อมทดสอบว่าข้อมูลใหม่ยังแสดงและสถานะออฟไลน์กลับมาปกติได้
- ใช้ตัวจัดรูปแบบจำนวนเงินและวันเวลาร่วมกัน และคำนวณรายการเมนูใหม่เฉพาะเมื่อข้อมูล/ตัวกรองเปลี่ยน
- ให้รูปเมนูแถวแรกโหลดก่อน รูปถัดไปยังโหลดตามระยะการเลื่อน
- เปลี่ยนฟอนต์ 8 ไฟล์เป็น WOFF2 โดยเก็บชุดอักษรและน้ำหนักเดิม รวมขนาดไฟล์ 387,440 → 173,480 B มีชื่อไฟล์ตาม hash เพื่อรองรับแคช
- เพิ่ม public/_headers สำหรับแคชไฟล์ที่มีชื่อเปลี่ยนตามเนื้อหา ส่วน HTML และรายการฟอนต์ตรวจเวอร์ชันใหม่ทุกครั้ง การเรียกข้อมูลลูกค้าใช้ no-store

## ฐานข้อมูล

เพิ่ม migration 007 และไฟล์ `supabase/performance-upgrade.sql` ซึ่งสร้างดัชนี `order_items(order_id,line_number)` เท่านั้น ไม่เปลี่ยนข้อมูลออเดอร์ สิทธิ์ หรือขั้นตอนรับเงิน

ผลบน PostgreSQL 16 ในฐานข้อมูลชั่วคราว มี 1,000 ออเดอร์/5,000 รายการอาหาร: ค่ากลาง snapshot 5 รอบ 101.9 → 72.0 ms ลดประมาณ 29% และ JSON ก่อน–หลังเท่ากัน ผลนี้ขึ้นกับจำนวนข้อมูลและเครื่องฐานข้อมูล ไม่ใช่ผลวัดบน Supabase จริง

**ดัชนีนี้ยังไม่ได้รันบน Supabase จริง** ร้านที่ติดตั้ง migration 1–6 แล้วใช้ไฟล์ performance-upgrade.sql ได้โดยตรง ส่วน setup.sql/upgrade.sql รวมดัชนีไว้สำหรับติดตั้งตามขั้นตอนเดิมแล้ว

## ตรวจสอบแล้ว

- Unit tests 206 รายการผ่าน
- Browser workflow checks 30 กรณีผ่าน ครอบคลุมตะกร้า ออเดอร์ที่คำตอบหาย การรับเงิน การเปลี่ยนบัญชี การแจ้งเตือนข้ามแท็บ การตั้งค่า และ QR สำหรับพิมพ์
- ทดสอบฐานข้อมูล PostgreSQL ชั่วคราวผ่าน ทั้งสิทธิ์ ความถูกต้องของข้อมูล ติดตั้งซ้ำ และการเพิกถอนเครื่องระหว่างมีคำสั่งรอทำงาน
- Production benchmark ผ่านการตรวจว่าหน้าลูกค้าไม่โหลดโค้ดหลังบ้าน หยุด polling ตอนซ่อนแท็บ และกลับมาดึงทันที
- ตรวจฟอนต์ภาษาลาว/ไทยและหน้าจอมือถือไม่มีเนื้อหาล้นแนวนอน พร้อมตรวจภาพหน้าจอ
- Build ผ่าน และตรวจว่าไฟล์เว็บไม่มี device credential ส่วนตัว
- การตรวจ transport กับ Supabase จริงเป็นการอ่านความพร้อมและเมนูเท่านั้น ไม่สร้างออเดอร์หรือรับเงินจริงเพื่อทดสอบ

## การนำผลไปใช้และข้อจำกัด

ไฟล์เว็บพร้อมอัปโหลดอยู่ที่ `.local/performance/khaopiek-performance-web.zip` ต้อง deploy จึงมีผลบนโทรศัพท์ที่เปิดเว็บออนไลน์ และต้องรัน performance-upgrade.sql จึงได้ประโยชน์จากดัชนีบน Supabase

การตรวจ HTTP รอบนี้ ลิงก์ Workers เดิม `https://lingering-field-fc0c.darkside404404.workers.dev/` ตอบ 404 จึงยังยืนยันการใช้งานออนไลน์จากลิงก์นั้นไม่ได้ ไม่มีการเปลี่ยนโดเมนหรือเผยแพร่เว็บในงานรอบนี้

ระบบหลังบ้านยังดึงประวัติทั้งหมดใน snapshot ถ้ามีข้อมูลสะสมมาก ควรแยกประวัติ/รายงานเป็นหน้าข้อมูลและให้หน้าโต๊ะรับเฉพาะข้อมูลล่าสุด การทดสอบครั้งนี้ใช้ browser จำลอง ยังควรลองบนโทรศัพท์/แท็บเล็ตจริงและอินเทอร์เน็ตที่ร้าน

## ทำซ้ำการวัด

เครื่องมือ `tests/browser/performance-qa.mjs` ใช้ Playwright กับ browser ที่ติดตั้งไว้ โดยรับตำแหน่งผ่าน PLAYWRIGHT_MODULE และ BROWSER_EXECUTABLE

```sh
node tests/browser/performance-qa.mjs --dist dist --label final --runs 3 \
  --output .local/performance/final.json \
  --baseline .local/performance/before.json \
  --image-root .local/performance/before/images \
  --assert-split --polling --visual
```

หลักฐานรอบนี้อยู่ใน `.local/performance/`: before.json, final.json, database-index.json, ภาพ final-guest.png/final-guest-th.png/final-staff.png และ log การตรวจต่าง ๆ โฟลเดอร์นี้ไม่ถูกส่งขึ้น Git

อ้างอิงพฤติกรรมการแยก CSS ของ [Vite](https://vite.dev/guide/features#css-code-splitting) และการใช้ _headers กับ [Cloudflare Workers Static Assets](https://developers.cloudflare.com/workers/static-assets/headers/)
